# V0.3 Remaining Modules Portfolio Value Audit

审计对象：原 `hr-cost-dashboard` 剩余模块

审计范围：数据导入、映射配置、权限管理、数据库管理（只读意图）、原总览页

审计方式：只读检查原项目页面、组件、API、数据层和历史交接材料；未修改原项目或公开仓库业务代码、数据和 Git 历史。

## 1. 结论摘要

当前公开仓库已经冻结并本地提交：预算进度、薪资分析、人力成本评估、明细查询。这四个模块共同构成了公开作品集最完整的“分析用户旅程”：选择期间与组织范围 → 查看指标和趋势 → 比较岗位结构 → 查询合成明细。

原系统剩余模块主要服务于后台治理，而不是招聘作品集中的分析用户：

| 模块 | 原系统实际定位 | 公开作品集推荐 | 推荐理由 |
|---|---|---|---|
| 数据导入 | CSV/Excel 到 PostgreSQL、标准化表、业务表的写入流水线 | Architecture/documentation only | 真实导入会牵涉文件、数据库写入、批次追溯和权限；展示价值应转化为架构说明 |
| 映射配置 | 组织、岗位、薪资组成、成本和一线范围等业务映射治理 | Architecture/documentation only | 技术上重要，但映射值本身高度企业专属；不宜把企业规则伪装成公开配置中心 |
| 权限管理 | 飞书组织同步、角色和组织范围授权 | Do not migrate | 暴露身份、组织和权限边界；公开版没有真实多租户或登录后端可支撑 |
| 数据库管理（只读） | 数据表、字段字典、维度规则、导入血缘和质量检查概览 | Simplified portfolio reconstruction（静态架构页内） | “数据治理可观测性”有招聘价值，但原页面 GET 仍会初始化/写入 metadata，不能直接称为严格只读 |
| 原总览页 | 汇总预算、KPI、薪酬、人力成本评估的管理入口 | Simplified portfolio reconstruction（未来独立项目概览） | 可借鉴信息层级和用户旅程，不复用原企业 KPI、权限门禁或聚合实现 |

核心判断：**不要因为原系统有后台页面就把后台能力迁移到 GitHub Pages。** 公开作品集应展示可解释的分析产品、可靠的数据边界和清晰的架构取舍，而不是没有真实后端支撑的“假导入、假权限、假数据库”。

## 2. 评价标准

本审计把“系统真实存在过”和“值得公开展示”分开判断：

- **招聘作品集价值**：是否能帮助 HR、HR Tech 或 People Analytics 面试官理解产品判断、数据治理、指标可靠性或用户旅程。
- **公开安全性**：是否会暴露员工身份、组织层级、企业规则、连接信息、权限模型或真实业务流程。
- **静态可运行性**：是否能在 Next.js static export / GitHub Pages 下无需服务器完成核心交互。
- **可信度**：公开演示是否会让人误以为存在真实企业导入、权限或数据库能力。
- **实现成本**：是否需要重新建立公共数据层、认证、持久化、审计和失败恢复机制。

## 3. 数据导入

### 3.1 原模块实际解决的问题

`app/import/page.tsx` 是运营后台入口，用于选择业务数据类型、上传 CSV、校验表头和字段类型、写入 PostgreSQL，并查看上传批次和预览结果。页面支持薪资明细、预算、人力成本、岗位配比及若干 KPI/配置型数据；固定模式会覆盖同期间数据，保留 `raw_uploads` 追溯记录，并在导入完成后刷新多个展示 API。

页面还提供：

- 数据类型选择和模板下载；
- CSV 拖拽上传；
- 必填字段、更新关键字段和未映射字段提示；
- 导入结果、错误行、跳过行、标准化行数和目标表信息；
- 上传历史表和本人上传记录清除；
- FastAPI / PostgreSQL 健康检查。

### 3.2 依赖与风险

| 依赖 | 证据位置 | 风险 |
|---|---|---|
| 上传 Route Handler | `app/api/upload/route.ts` | 动态服务器能力，GitHub Pages 无法承载 |
| PostgreSQL 写入 | `lib/postgres-import.ts`、`lib/postgres.ts` | 文件内容、数据库连接、写入和回滚风险 |
| FastAPI 健康检查 | `app/api/upload/health/route.ts` | 外部服务 URL、运行时依赖和部署耦合 |
| NextAuth / session | `app/api/upload/route.ts`、`lib/auth.ts` | 上传者身份和个人历史记录依赖登录 |
| raw/standardized/business 多层写入 | `lib/postgres-import.ts` | 需要企业表结构、字段字典和批次治理 |
| 刷新展示 API | `app/import/page.tsx` | 导入后触发的 API 列表属于原系统编排，不适合公开复制 |

导入字段配置还会将未识别字段保留到 `details_json`。这类“宽松保留原字段”的设计在企业内部便于追溯，但公开仓库中会造成未知字段泄漏风险。

### 3.3 公开保留与重建建议

可以保留：

- “数据进入系统前需要校验、标准化、记录批次”的产品思想；
- 模板下载、字段校验、预览和错误反馈的 UI 语义；
- 一张静态的 synthetic pipeline 图，说明 `CSV → public adapter → synthetic JSON → 页面`。

必须重建或删除：

- 不复制上传 API、PostgreSQL 写入、FastAPI health、raw_uploads 和真实批次；
- 不接受任意用户 CSV 并声称写入系统；
- 不展示真实文件名、业务表名、上传者、行号或企业字段；
- 如果未来要做交互演示，只能做浏览器端“导入预览模拟器”，明确它不会持久化，也不会改变冻结页面数据。

### 3.4 价值、成本和结论

- 招聘价值：中。对 HR Tech / 数据产品岗位有价值，但对 People Analytics 分析岗位低于已完成的四个分析页面。
- 实现成本：高。真正迁移需要安全的文件解析、schema registry、校验、版本、持久化、错误恢复和权限审计。
- 风险：极高。文件、真实薪资、员工身份、数据库写入和导入覆盖规则可能同时泄漏。
- 推荐：**Architecture/documentation only**。未来如需产品设计展示，做“导入治理流程图 + synthetic schema validation”而非真实导入后台。

## 4. 映射配置

### 4.1 原模块实际解决的问题

`app/mapping-config/page.tsx` 维护三类 roster mapping（组织、岗位-组织、岗位维度）以及薪资构成、岗位维度和一线组织范围等配置表。它允许下载模板、上传配置 CSV、选择追加/覆盖/upsert 模式、查看校验和上传状态，并导出当前数据库映射。

页面实际覆盖：

- 薪资构成到成本/预算分类的映射；
- 岗位、管理方式、组织范围和预算岗位分类；
- 一线组织范围；
- 配置版本与 active/draft 状态；
- 花名册拆出的组织、岗位组织和岗位维度映射；
- 上传批次、目标表、字段识别和未映射字段。

### 4.2 依赖与敏感性

| 类型 | 证据位置 | 公开风险 |
|---|---|---|
| 配置版本读写 | `app/api/mapping-config/route.ts` | PostgreSQL、版本激活和写入事务 |
| roster import/export | `app/api/roster-mappings/*`、`lib/roster-mappings.ts` | 组织、岗位和企业字典直接暴露 |
| 业务成本 mapping | `lib/default-mapping-rules.ts`、`lib/payroll-kpi-business-mapping.ts` | 企业成本、KPI、奖金和聚合规则风险 |
| 上传者身份 | `getServerSession`、`uploaded_by` | 个人身份和审计记录 |
| dynamic route | `runtime = "nodejs"`、`force-dynamic` | 无法作为静态页面直接部署 |

“映射”表面上是通用配置，但实际 value 往往就是企业业务规则：哪些薪资项计入人力成本、哪些字段视为 KPI、岗位如何归类、哪些组织属于一线。公开展示这些值会把脱敏后的 UI 重新连接到原企业口径。

### 4.3 公开保留与重建建议

可以保留：

- “事实数据”和“解释事实的维表/映射”应分离的架构原则；
- 版本、draft/active、校验和回滚的概念图；
- 公开 synthetic role/organization dimension 的静态数据字典。

必须重建或删除：

- 不复制原映射值、岗位名、组织路径、成本科目、KPI 规则或 source mapping；
- 不复制写入/激活 API、数据库表和上传导出能力；
- 公开 adapter 只能读取仓库内虚构维表，不能让访客编辑后改变分析口径；
- 如需交互，使用本地只读“映射预览”或架构说明，不提供伪造的企业配置中心。

### 4.4 价值、成本和结论

- 招聘价值：中到高，尤其适合展示数据治理和指标建模能力，但必须讲“公共 schema 设计”而不是企业规则。
- 实现成本：中到高；只做静态架构说明为低，做可编辑版本治理为高。
- 风险：高，尤其是岗位/组织映射、成本组成和 KPI 关联。
- 推荐：**Architecture/documentation only**；不做 faithful sanitized migration。

## 5. 权限管理

### 5.1 原模块实际解决的问题

`app/admin/page.tsx` 是超级管理员后台。页面先调用 `/api/admin/access` 判断访问资格，再读取权限、组织和用户数据。它支持：

- 同步飞书组织架构；
- 展示部门树、成员数和已同步用户；
- 给部门配置角色和可查看区域；
- 添加用户兜底权限；
- 角色包括管理员、HRBP 等；
- 通过 session、邮箱、飞书 ID 和权限表限制访问。

### 5.2 依赖与风险

关键依赖包括：

- `next-auth` 和飞书 OAuth provider；
- `FEISHU_APP_ID`、`FEISHU_APP_SECRET`、`NEXTAUTH_SECRET` 等 secrets；
- `feishu_departments`、`feishu_users`、`feishu_user_departments`、`person_permission_scope` 等身份/组织表；
- `lib/permission.ts` 的 L1/L2/L3、admin/BP/L3 规则和 C1-C5 scope；
- `/api/org`、`/api/org/permission`、`/api/permission` 的同步及写入操作。

这不是普通 UI 组件：它定义了谁能看什么数据。没有真实身份 provider、后端 session、审计日志和服务端强制过滤，公开版的“权限管理”只能是假功能。

### 5.3 公开保留与重建建议

原则上必须删除：

- 飞书登录、组织同步、邮箱、Open ID、用户姓名、员工/部门 scope；
- 真实角色授权 API、管理员门禁、session 和 permission tables；
- 任何暗示公开站点提供企业级访问控制的页面。

可以在架构页用一张不带真实值的示意图说明：生产系统需要 authentication、authorization、row-level filtering 和 audit log；但必须明确这是设计说明，不是公开站点已实现的能力。

### 5.4 价值、成本和结论

- 招聘价值：高（对 HR Tech / 平台工程），但价值来自架构决策，不来自复制管理后台。
- 实现成本：极高。需要完整身份、组织同步、权限缓存、后端过滤和审计。
- 风险：极高，涉及个人身份、组织结构、权限绕过和 secrets。
- 推荐：**Do not migrate**；仅在 Architecture 页面做无数据的安全边界说明。

## 6. 数据库管理（只读）

### 6.1 原模块实际解决的问题

`app/database/page.tsx` 试图提供一个只读数据资产目录，内容包括：

- 托管表数量、总记录数、最新薪资/预算期间和最近上传时间；
- 核心数据表、粒度、记录数、字段数和关键字段完整率；
- 数据质量检查；
- 标准字段字典；
- 城市、岗位、职级和薪资性质维度规则；
- source type → target table → display API 的导入链路；
- 上传批次、验证状态和消费模块。

这是剩余模块中最有作品集价值的一个，因为它能展示 data lineage、schema governance 和 quality observability，而不仅是图表。

### 6.2 “只读”边界审计

页面 GET `/api/database/overview` 使用 PostgreSQL，并调用 `ensureMetadataTables()` / `ensureUploadSourceMappings()` 等初始化逻辑。原交接材料也明确记录：该 GET 存在 metadata DDL 初始化副作用，因此它是“只读视图意图”，不是严格数据库 read-only。

同时存在以下风险：

- 直接展示表名、字段、记录数、期间和来源映射；
- `details_json`、上传批次和 source file 可能携带内部信息；
- 运行时依赖数据库、动态 Route Handler 和真实 schema；
- 质量规则与企业字段口径绑定；
- 页面说明“不会修改数据库”与实际初始化 DDL 不完全一致。

### 6.3 公开保留与重建建议

推荐把它重建为静态的 **Data Architecture / Governance** 页面，而不是“数据库管理”：

- 使用完全虚构的 schema metadata；
- 只展示公开仓库已经存在的 synthetic layers：salary facts、evaluation facts、budget facts、detail explorer；
- 展示字段类别、粒度、唯一键、adapter 边界和质量检查结果；
- 质量检查只验证仓库内 JSON，不连接数据库、不执行 DDL、不显示真实行数；
- 明确“静态演示，不提供数据库管理或写入能力”。

不应直接复制原数据库管理页面，因为那会把企业数据目录、导入批次和内部 API 血缘暴露出来。

### 6.4 价值、成本和结论

- 招聘价值：高，尤其对 People Analytics、Analytics Engineering、HR Tech 和数据产品岗位。
- 实现成本：中。静态架构页可控，真实只读数据库管理则高。
- 风险：中到高，主要是 schema/来源泄漏和“只读”表述不实。
- 推荐：**Simplified portfolio reconstruction**，未来单独设计；不迁移原页面的数据库链。

## 7. 原总览页（仅作参考）

### 7.1 原页面真实作用

`app/page.tsx` 是受权限门禁保护的聚合入口。它先请求 `/api/overview/access`，再请求全局月份/组织筛选选项，按月份组合：

1. 预算与管控概览；
2. 一线人效与业务 KPI 监控；
3. 薪酬结构与趋势；
4. 人力成本明细与岗位配比。

它的价值是缩短管理用户从“当前月份”到多个业务页面的路径；它不是新的独立业务事实源。

### 7.2 为什么不直接迁移

- 依赖 `/api/overview/access`、全局筛选 API 和多个业务 API；
- 聚合了原企业 KPI、费用率、岗位配比和权限门禁；
- 页面文案和布局能高保真复制，但业务口径容易被误认为已统一；
- 公开仓库已经将“项目概览”保留为独立招聘作品集页面，不需要恢复原总览。

### 7.3 值得以后吸收的信息

未来的 Portfolio Overview 可以吸收以下信息架构，而不是原代码：

- 项目目标和数据边界；
- 四个已冻结分析模块的入口卡片；
- 每个页面解决的分析问题；
- `synthetic data → public adapter → static UI` 数据链；
- 已主动排除的企业权限、API 和数据库能力；
- 页面截图、关键交互和技术取舍。

应删除/重建：

- 权限门禁；
- 一线 KPI / 费用率聚合；
- 原总览的 API 复用组件；
- 原企业月份、组织和异常规则。

推荐：**Simplified portfolio reconstruction**，但不作为本轮模块迁移。

## 8. 跨模块敏感性与技术风险

1. **真实文件和员工数据泄漏**：导入和映射入口天然接受或显示 CSV、文件名、姓名、工号、组织、岗位、薪资和来源字段。
2. **企业规则泄漏**：成本组成、岗位映射、一线范围、KPI/奖金关联和覆盖期间规则可能反推出内部管理口径。
3. **身份与权限泄漏**：飞书 Open ID、邮箱、部门树、scope 和角色不应进入公开仓库或静态页面。
4. **服务器链复活**：Route Handler、PostgreSQL、FastAPI、NextAuth、session 和环境变量会破坏 static export 的边界。
5. **伪造能力风险**：没有持久化和后端强制授权时，展示可写导入、可编辑映射或可管理权限会误导招聘方。
6. **只读表述不准确**：数据库管理 GET 的 metadata 初始化 DDL 与严格 read-only 要求冲突。
7. **后台能力稀释作品集主题**：过多后台页会让招聘方看不到已完成的指标、交互和数据解释能力。

## 9. 推荐实施顺序

### 顺序 0：保持当前四个分析模块冻结

不再为了后台完整性修改 Budget、Salary、Evaluation、Detail Query，也不重新引入原总览。

### 顺序 1：完善现有 Portfolio Overview（未来单独任务）

用公开项目目标、模块卡片、数据边界、截图和架构图组织招聘作品集入口。只使用当前 synthetic 数据和已冻结页面的公开结果。

### 顺序 2：静态 Data Architecture / Governance 页面

优先展示 shared employee-month universe、public adapters、schema 粒度、唯一键、验证脚本和静态导出边界。该页面的招聘价值高、风险可控。

### 顺序 3：可选的浏览器端 schema validation demo

如果需要体现导入思维，只做本地 CSV 解析/字段检查预览，不写数据库、不保存文件、不刷新业务页面，并明确“仅为客户端演示”。这不是原数据导入页的迁移。

### 顺序 4：不实施权限管理迁移

仅保留架构说明和安全边界，不模拟真实组织树、用户、角色和 scope。

## 10. Remaining Modules Decision Matrix

| 模块 | 原业务问题 | UI/交互保留价值 | 数据/技术依赖 | 公开展示价值 | 实现成本 | 风险 | 最终决策 |
|---|---|---|---|---|---|---|---|
| 数据导入 | 将文件校验、标准化并写入业务数据层 | 上传、模板、预览、错误反馈有参考价值 | PostgreSQL、FastAPI、Route Handler、session、批次表 | 中（HR Tech 较高） | 高 | 极高 | **Architecture/documentation only** |
| 映射配置 | 管理组织、岗位、成本和业务字段映射 | 版本、校验、active/draft 有参考价值 | PostgreSQL、企业字典、成本/KPI 规则、roster mapping | 中到高 | 中到高 | 高 | **Architecture/documentation only** |
| 权限管理 | 控制用户和组织范围的数据访问 | 权限矩阵和 scope 设计有参考价值 | 飞书 OAuth、NextAuth、session、身份表、后端强制过滤 | 高（平台岗位） | 极高 | 极高 | **Do not migrate**；仅安全架构说明 |
| 数据库管理（只读意图） | 观察数据资产、字段口径、质量和血缘 | Tabs、表目录、字段字典、质量卡有参考价值 | PostgreSQL、动态 API、metadata DDL、内部表名/来源 | 高 | 中（静态重建）/高（真实 DB） | 中到高 | **Simplified portfolio reconstruction** |
| 原总览页 | 作为多模块管理入口 | 信息层级和入口卡片有参考价值 | 权限门禁、多个业务 API、原 KPI/费用率 | 中到高 | 中 | 高 | **Simplified portfolio reconstruction**，未来独立项目概览 |

## 11. 最终建议

1. 当前四个已冻结模块已经足以构成可信的公开分析产品，不需要补齐后台治理页面来证明“系统完整”。
2. 如果目标是 HR / People Analytics 招聘，优先展示指标定义、数据边界、交互和验证结果；如果目标是 HR Tech / Analytics Engineering，再增加静态数据架构与治理说明。
3. 数据导入、映射配置和权限管理不应以 faithful sanitized migration 形式进入公开仓库。它们最重要的内容是架构思想，不是原页面和原企业规则。
4. 数据库管理适合重建为静态 Data Architecture / Governance 页面，但必须避免“数据库管理”“只读连接”“实时行数”等会暗示真实后端的表述。
5. 原总览仅提供未来 Portfolio Overview 的信息架构参考；不恢复原总览页面，也不复制其 API、权限或企业 KPI 聚合。

审计结论：公开项目下一阶段应从“迁移更多原页面”转向“讲清已完成产品的用户旅程、数据契约和工程取舍”。
