# V0.3 Portfolio Overview — Phase 0 Content Freeze

状态：文案冻结稿，未实施

适用页面：公开招聘作品集首页“项目概览”

目标读者：HR、People Analytics、AI-HR、HR Tech / 数据产品招聘者

本稿只冻结信息优先级和显示文案，不修改现有 Information Architecture Spec、页面、数据或业务模块。

## 1. 首页最终信息优先级

```text
HR / People Analytics 问题
        ↓
产品与指标判断
        ↓
四个分析模块
        ↓
数据可信与公开边界
        ↓
AI-assisted development
        ↓
技术架构
```

首页不以 React、Next.js、UI migration 或 adapter 作为主叙事。技术内容保留，但放在招聘者已经理解业务价值之后。

## 2. 最终首页模块顺序

1. Hero：项目定位与主要入口
2. 项目解决的问题：统一查看、解释结构、复核口径
3. 我的职责：产品判断、指标定义、数据边界和交付验证
4. 四个核心分析模块：预算、薪资、成本评估、明细查询
5. Project Scope：公开项目实际覆盖范围
6. 数据可信与公开边界：synthetic data 和不包含的能力
7. AI-assisted Development：AI 的辅助角色与人工责任
8. Architecture CTA：系统架构说明入口
9. Scope boundary：明确未迁移的后台和企业专属能力

## 3. Hero 文案冻结

### 主标题

> People Analytics Dashboard

### 副标题

> 面向 HR 与 People Analytics 的公开分析产品案例：从预算使用、薪资结构、人力成本到明细查询，建立一条可筛选、可解释、可复核的分析旅程。

### 边界说明

> 本项目使用完全虚构的 synthetic data。公开 Demo 不连接原企业 API、数据库、身份系统或权限系统。

### Hero CTA

主 CTA：

> 查看四个分析模块

次 CTA：

> 了解系统架构

Hero 不显示人数、成本、薪资、营收、订单、KPI 或任何“实时经营”数字。

## 4. “项目解决的问题”文案冻结

模块标题：

> 这个项目解决什么问题？

引导句：

> People Analytics 的难点不只是展示数字，而是让不同粒度的数据在同一筛选范围下保持可解释、可比较、可复核。

### 卡片一：统一查看

标题：

> 把分散的人力信息放进同一分析旅程

正文：

> 以月份和组织范围为入口，依次查看预算使用、薪资结构、人力成本和员工月度明细，减少在多个孤立表格之间切换。

### 卡片二：解释结构

标题：

> 从总量继续追问“由什么组成”

正文：

> 通过薪资组成、岗位结构、HC 占比与成本占比、趋势和下钻明细，帮助使用者理解数字的组成，而不是只看一个汇总值。

### 卡片三：复核口径

标题：

> 让指标的分母、粒度和缺失状态可见

正文：

> 明确 HC、employee-month、总额/人数、人力成本组成以及 0 与缺失的区别，避免把不可计算的结果伪装成 0 或无限值。

这一区域禁止使用“自动发现绩效问题”“保证经营决策正确”“实时掌握企业全貌”等超出公开 Demo 证据的表述。

## 5. “我的职责”文案冻结

模块标题：

> 我的职责

引导句：

> 我负责把一个复杂的人力分析产品拆成可公开验证的用户旅程，并对指标、数据边界和最终体验负责。

最终职责列表：

- 将 HR / People Analytics 问题拆解为预算、薪资、成本评估和明细查询四个分析场景；
- 定义 HC、employee-month、人均值、成本组成、趋势和岗位结构等公开指标的计算边界；
- 设计共享的 synthetic employee-month universe，确保 Salary、Evaluation 与 Detail 使用一致事实；
- 将原授权 UI 的高价值布局和交互迁移为公开安全的浏览器端体验；
- 移除真实数据、企业 API、数据库、身份、权限和内部 KPI 规则；
- 通过数据校验、静态构建、浏览器交互检查和视觉验收确认交付质量；
- 对每个未迁移能力做出明确取舍，而不是为了页面完整而制造虚假后台能力。

职责列表可以提到“Public Adapter”和“static export”，但它们必须作为实现手段出现，不作为首页主价值主张。

## 6. 四个模块入口卡文案冻结

入口顺序固定为：

```text
预算进度 → 薪资分析 → 人力成本评估 → 明细查询
```

### 6.1 预算进度

卡片标题：

> 预算进度

分析问题：

> 预算与实际使用之间如何随月份和组织范围变化？

卡片正文：

> 查看人力成本、HC 和人均成本的预算/实际对比，支持当月与年初至今视图，并展开明细表复核组成。

交互标签：

> 月份 · 组织范围 · 当月/累计 · 趋势 · 明细展开

CTA：

> 查看预算进度

### 6.2 薪资分析

卡片标题：

> 薪资分析

分析问题：

> 薪资总额、薪资组成和岗位/区域结构如何随时间变化？

卡片正文：

> 从薪资组成、岗位结构和人均税前薪资趋势出发，比较不同岗位组、等级与区域层级的公开 synthetic 事实。

交互标签：

> 全局筛选 · 选月 · Tooltip · Collapse · 岗位比较 · 区域比较

CTA：

> 查看薪资分析

### 6.3 人力成本评估

卡片标题：

> 人力成本评估

分析问题：

> HC、总人力成本、人均成本和岗位结构之间有什么可解释的关系？

卡片正文：

> 联动查看当前 HC、人力成本、人均成本、成本环比、HC/成本趋势，以及岗位组的 HC 占比、成本占比和结构差。

交互标签：

> 月份 · 组织范围 · 岗位组 · 双趋势 · 结构比较 · 明细表

CTA：

> 查看人力成本评估

### 6.4 明细查询

卡片标题：

> 明细查询

分析问题：

> 如何从分析结果下钻到可复核的 employee-month 薪资事实？

卡片正文：

> 在公开 synthetic salary facts 上进行关键词、月份、组织、岗位组、等级和地点筛选，支持排序、分页、聚合和 CSV 导出。

交互标签：

> 多维筛选 · 搜索 · 排序 · 分页 · 聚合 · CSV

CTA：

> 查看明细查询

四张卡统一使用“分析问题 → 能看到什么 → 如何交互”的结构，不显示真实规模或企业业务结果。

## 7. Project Scope 文案冻结

模块标题：

> Project Scope

引导句：

> 公开项目聚焦一条完整但可控的 People Analytics 分析旅程。

只展示以下项目自身信息：

| Scope item | 最终显示文案 |
|---|---|
| 核心模块 | 4 个核心分析模块：预算进度、薪资分析、人力成本评估、明细查询 |
| 事实粒度 | 统一使用 employee-month 作为公开分析事实粒度 |
| 时间分析 | 支持月度趋势和选月对比 |
| 交互方式 | 支持多维筛选、排序、分页、展开和下钻 |
| 数据边界 | 使用完全虚构的 synthetic data，不代表任何企业、行业或市场基准 |
| 发布方式 | Next.js static export，可在 GitHub Pages 上查看 |

Project Scope 禁止出现：真实人数、总成本、薪资区间、营收、订单、KPI、企业名称、组织规模或“覆盖多少员工/部门”等暗示真实规模的内容。

## 8. 数据可信与公开边界文案冻结

模块标题：

> 数据可信与公开边界

正文：

> 公开版保留可解释的分析结构和交互方式，但不公开原系统的企业数据链。所有展示数据均来自仓库内的 synthetic JSON，并通过 Public Adapter 和纯函数计算生成页面结果。

边界清单：

- 不包含真实员工姓名、邮箱、手机号或工号；
- 不包含原企业组织、岗位、薪资、KPI、订单或营收；
- 不连接原企业 API、PostgreSQL、FastAPI、身份或权限系统；
- Salary、Evaluation 与 Detail 共用公开 employee-month universe；
- 0、缺失和不可计算状态按公开规则分别处理。

推荐链路标签：

```text
Synthetic JSON → Public Adapter → Calculation Layer → Static UI
```

## 9. AI-assisted Development 文案冻结

### 页面标题

> AI-assisted Development

### 最终短文案

> Generative AI 用于代码探索、实现辅助与测试；业务需求拆解、指标定义、数据边界、产品取舍与最终验收由人工负责。

### 轻量补充说明

> AI 可以帮助分析依赖、生成验证草案和加速迭代，但不会替代对 HR 业务口径、隐私风险或公开可信度的判断。

### 视觉优先级

- 不放在 Hero 主视觉中；
- 不作为第一张内容卡；
- 放在 Project Scope 与 Architecture CTA 之后，作为工作方法说明；
- 不展示未经核验的“AI 自动完成”“AI 自动决策”或模型性能数字。

## 11. 首屏与第二屏内容边界

### 首屏必须包含

1. 项目标题和 HR / People Analytics 定位；
2. 一句话说明解决的问题；
3. 主 CTA 与架构 CTA；
4. 一行 synthetic data / public boundary 说明；
5. 不超过三条的核心业务价值：统一查看、解释结构、复核口径。

首屏不包含：技术栈列表、长篇迁移过程、后台模块、完整风险清单或大量数字。

### 第二屏必须包含

1. 我的职责；
2. 四个核心模块入口卡；
3. Project Scope；
4. 一条轻量数据边界说明。

第二屏可以让招聘者开始点击业务页面，但不要求先阅读 Architecture 或 AI workflow。

### 第二屏之后

按顺序放置：AI-assisted Development → Architecture CTA → 未迁移能力边界。技术架构是信任和深入阅读入口，不是首页第一卖点。

## 12. 目标岗位语言检查

| 目标岗位 | 页面应让对方感受到 | 本稿对应内容 |
|---|---|---|
| HR | 能理解人力数据使用场景和分析价值 | 项目问题、四个模块、自然语言指标说明 |
| People Analytics | 关注分母、粒度、趋势、结构和复核 | 复核口径、employee-month、模块卡、明细查询 |
| AI-HR | 能将 AI 放进可靠的人力产品流程 | AI-assisted Development 的人机责任边界 |
| HR Tech / 数据产品 | 能做数据契约、产品取舍和安全边界 | 我的职责、Project Scope、数据边界、Architecture CTA |

应避免的整体观感：

- 只是在展示前端组件和图表；
- 只是在描述一次代码迁移；
- 只是在列技术栈；
- 伪装成真实企业系统或可用后台；
- 用大量数字证明“规模”，却没有说明口径和数据来源。

## 14. 冻结结论

本稿冻结的首页叙事为：

> 先说明 People Analytics 问题，再说明指标和产品判断；通过四个已完成分析模块展示用户旅程；随后解释 synthetic data 和公开安全边界；最后补充 AI-assisted development 与技术架构。

正式实现前，如需修改 Hero、职责、模块卡、Project Scope 或 AI 文案，应先更新本文件并重新进行人工内容验收。现有 Information Architecture Spec 不在本轮修改范围内。
