# V0.3 Portfolio Overview & Architecture Information Architecture

状态：设计稿，未实施

范围：公开招聘作品集的“项目概览”和“系统架构”信息架构

约束：不恢复原系统总览；不迁移数据导入、映射配置、权限管理或数据库管理后台；不修改 Budget、Salary、Evaluation、Detail Query、synthetic data 或 adapter。

## 1. 产品定位

公开站点不是原 HR 系统的公开镜像，而是一个可验证的 People Analytics 产品案例：

```text
问题定义 → 公开数据边界 → 可解释指标 → 分析交互 → 工程取舍 → 验证结果
```

招聘者首先看到的是“我解决了什么问题、如何做出取舍、怎样证明结果可靠”，而不是后台菜单数量。

### 1.1 目标受众

| 受众 | 2 分钟内最需要确认的内容 |
|---|---|
| HR / People Analytics | 能否把 HC、薪资、成本、岗位结构和明细查询组织成可解释的分析体验 |
| HR Tech / 数据产品 | 是否理解数据契约、筛选粒度、指标分母、异常/缺失状态和用户旅程 |
| Analytics Engineering / 前端 | 是否能把复杂业务 UI 迁移为静态、安全、可验证的 public adapter 架构 |
| 招聘经理 | 候选人的职责边界、交付结果、工具使用方式和对风险的判断 |

### 1.2 核心叙事

建议首页围绕一句话组织：

> 一个面向 People Analytics 的公开分析产品案例：用完全虚构的 employee-month 数据，展示预算、薪资、成本评估和明细查询如何共享口径并形成连续的分析旅程。

不要声称公开版仍连接企业 API、数据库、身份系统或真实业务指标。

## 2. Portfolio Overview 信息架构

项目概览应是招聘者的入口，不是 KPI 拼接页。推荐从上到下按以下层级排列：

1. **Hero：项目是什么、解决什么问题**
2. **My contribution：我负责什么**
3. **四个核心模块入口：从问题到页面**
4. **Data & safety boundary：为什么是 synthetic、哪些能力被移除**
5. **Build approach：Generative AI 如何参与，哪些判断由我负责**
6. **Architecture preview：链接到系统架构说明**
7. **Next / scope boundary：明确未迁移内容和未来方向**

## 3. 模块文案职责

### 3.1 Hero 文案

推荐主标题：

> People Analytics Dashboard

推荐副标题：

> 公开的 HR 分析产品案例：从预算使用、薪资结构到人力成本与明细查询。

辅助说明：

> 页面使用完全虚构的 synthetic data；公开版不连接原企业 API、数据库、身份或权限系统。

这段说明要可见，但不应压过产品价值成为首屏唯一信息。

### 3.2 项目问题模块

职责：解释为什么需要产品，而不是重复页面标题。

建议三列：

| 主题 | 文案职责 | 不应写成 |
|---|---|---|
| 统一查看 | 在同一月份/组织范围下比较预算、薪资和人力成本 | “实时掌握企业经营全貌” |
| 解释结构 | 从总量下钻到岗位结构、薪资组成和 employee-month 明细 | “自动发现绩效问题” |
| 复核口径 | 明确 HC、employee-month、总额/人数和缺失状态 | “保证业务决策正确” |

### 3.3 我的职责模块

推荐文案：

- 以原授权 UI 为参考，拆解页面层级、筛选交互和表格密度；
- 将企业数据链切换为独立 synthetic JSON 与 Public Adapter；
- 为 Salary / Evaluation / Detail 共享 employee-month 事实和维表边界；
- 明确人均指标分母、成本构成、active period 和缺失值处理；
- 通过 data validation、static build、浏览器交互和视觉验收收口；
- 使用 Generative AI 加速代码探索和测试，但由人工决定公开业务口径与安全边界。

不要使用“独立完成全部原系统”“复刻完整企业后台”等无法从公开仓库证明的表述。

### 3.4 AI-assisted build 模块

该模块的职责是展示工作方法，不把 AI 写成产品能力。

推荐结构：

| 阶段 | Generative AI 可参与 | 人必须负责 |
|---|---|---|
| 代码理解 | 依赖树、组件职责、候选迁移边界 | 授权范围、敏感字段判定和最终范围 |
| UI 迁移 | 组件草案、样式定位、交互测试脚本 | 是否保持原信息架构、视觉验收和回归判断 |
| 数据重建 | schema 草案、校验器和 adapter 模板 | synthetic 分布、指标公式和“不代表真实业务”的声明 |
| 质量收口 | 测试命令、diff/依赖扫描、浏览器检查清单 | 是否通过验收、哪些风险必须停止 |

建议展示一句：

> AI 负责加速探索与验证；产品口径、数据边界、公开安全和最终合并由我负责。

## 4. 四个业务页面入口设计

每张入口卡只回答三个问题：它分析什么、关键交互是什么、点击后看什么。

| 页面 | 标题 | 入口说明 | 关键交互 | CTA |
|---|---|---|---|---|
| Budget | 预算进度 | 按月份与组织范围查看预算使用、HC 和人均趋势 | 月份、组织、当月/累计、展开明细 | 查看预算进度 |
| Salary | 薪资分析 | 比较薪资组成、税前薪资趋势、岗位与区域结构 | 全局筛选、选月、Tooltip、Collapse、岗位/城市比较 | 查看薪资分析 |
| Evaluation | 人力成本评估 | 联动查看 HC、人力成本、人均成本、岗位结构与成本投入 | 月份/组织/岗位组、趋势、结构差和明细表 | 查看人力成本评估 |
| Detail | 明细查询 | 在 employee-month 粒度筛选、排序、分页和导出公开薪资事实 | 关键词、月份、组织、岗位/等级/地点、聚合、CSV | 查看明细查询 |

卡片底部可放一行“公开边界”：

> Synthetic data · 静态导出 · 无企业 API / DB / auth

不在卡片中放企业 KPI、订单、营收、费用率、异常排名或真实规模。

### 4.1 入口顺序

推荐顺序与用户旅程一致：

```text
预算进度 → 薪资分析 → 人力成本评估 → 明细查询
```

- 预算：先看“计划与实际”；
- 薪资：再看“薪资结构与趋势”；
- 评估：再看“成本投入与岗位结构”；
- 明细：最后做“筛选、复核和导出”。

## 5. 数据与安全边界模块

这部分是 Overview 的信任层，不是技术堆砌。推荐用一条简洁的双层对照：

```text
Public synthetic JSON
        ↓
Public Salary / Evaluation / Budget Adapter
        ↓
Pure calculations + browser filters
        ↓
Next.js static export / GitHub Pages
```

旁边列出四条保证：

- 没有真实员工姓名、邮箱、手机号或工号；
- 没有原企业组织、岗位、薪资、KPI、订单或营收；
- 没有 API Route、PostgreSQL、FastAPI、auth、session 或 permission；
- Salary、Evaluation、Detail 共用公开 employee-month universe；

要避免“完全还原真实系统”的表述。准确说法是：**高还原保留公开安全范围内的 UI、模块顺序和交互语义；数据层和企业规则已替换。**

## 6. System Architecture 信息架构

系统架构页的任务是解释能力边界，而不是伪造可操作后台。推荐页面顺序：

1. **一句话架构结论**：两个边界、一个公开运行时；
2. **Internal System（事实来源）**：仅作为抽象架构，不展示真实值；
3. **Public Portfolio（当前实现）**：展示仓库可验证链路；
4. **Boundary decisions**：保留、移除、重建三类能力；
5. **Data contract**：粒度、唯一键、维表和计算层；
6. **Case studies**：导入/映射如何转成架构案例；
7. **Static deployment and verification**：为什么能在 GitHub Pages 运行。

### 6.1 Internal System 抽象图

```text
业务文件 / 业务确认
        ↓
数据导入与标准化
        ↓
映射配置 / 维度治理
        ↓
PostgreSQL + 业务数据表
        ├─ Next.js API routes
        ├─ FastAPI 辅助链路
        └─ 身份 / 权限 / 组织 scope
                ↓
预算、薪资、成本评估、明细与总览
```

图中只写能力类别，不写真实数据库名、表名、URL、组织名、岗位名、文件名或权限值。旁注应明确：这是基于原项目事实的抽象，不是公开仓库当前运行的生产系统。

### 6.2 Public Portfolio 图

```text
data/public-*/ synthetic JSON
        ↓
Public adapters
  ├─ public-budget
  ├─ public-salary
  ├─ public-evaluation
  └─ public-detail
        ↓
Pure TypeScript filters / calculations / status policies
        ↓
React + Ant Design + ECharts UI
        ↓
Next.js static export → GitHub Pages
```

公开版可验证的关键事实：

- 没有 `app/api/**` 作为运行时数据入口；
- 没有数据库连接、认证、session 或权限依赖；
- 页面交互在浏览器端完成；
- 数据校验脚本和 build 检查属于发布前质量门；
- CSV 导出仅产生 synthetic salary detail 字段。

## 7. Internal System vs Public Portfolio 对照

| 能力 | 原内部系统真实存在 | 公开版处理 | 页面表达 |
|---|---|---|---|
| 数据文件导入 | 有，包含 CSV/标准化/业务表写入 | 移除运行时写入；仅说明 pipeline 思路 | Case Study / Architecture |
| 映射配置 | 有，涉及岗位、组织、成本和 KPI 分类 | 移除企业 mapping；仅说明维表与版本治理概念 | Case Study / Architecture |
| PostgreSQL | 有 | 移除连接、查询和写入 | Boundary decision |
| FastAPI / API | 有多条运行时链路 | 移除 Route Handler 和外部服务 | Boundary decision |
| 分析模块 | 有，公开版已按安全边界迁移四页 | 使用 Public Adapter + synthetic facts | 业务入口卡片 |
| 身份 / 权限 | 有，依赖 OAuth/session/组织 scope | 不迁移，不模拟登录 | Security boundary |
| 总览 | 有，聚合多个业务模块并受权限控制 | 不复用；未来做招聘作品集 Overview | Product decision |
| 数据库管理 | 有只读意图，但 GET 有 metadata 初始化副作用 | 不迁移；未来静态治理页 | Architecture case |
| 导出 | 原系统有服务端导出 | Detail 仅浏览器端导出固定 synthetic 白名单 | Detail 页面说明 |

## 8. 数据导入 / Mapping 的 Case Study 呈现

### 8.1 导入 Case Study

不要做“上传文件”按钮。使用三栏静态说明：

1. **Problem**：原系统需要把多种业务文件变成可消费的标准事实；
2. **Design**：landing → validation → standardization → mapping → consumers；
3. **Public decision**：公开版移除写库与身份链，用仓库内 synthetic JSON 和 adapter 验证相同的数据边界。

可展示的 artefact：

- 脱敏后的字段类别图；
- employee-month 唯一键示意；
- missing / zero / invalid 的校验规则；
- 一个不包含真实值的 validation checklist。

### 8.2 Mapping Case Study

不要展示原企业岗位、组织或成本科目。使用概念化的 mapping card：

```text
Raw field category → public canonical field → consumer module
```

可展示：

- 维表为什么独立于事实表；
- active/draft/version 为什么是治理问题；
- mapping 改动为何需要重新验证计算和页面；
- public adapter 如何显式读取虚构 role/org/location labels。

不可展示：

- 原 mapping CSV；
- 原岗位/组织路径；
- 企业成本或 KPI 换算；
- 上传者、文件名、批次 ID、源行号和数据库表名。

## 9. 招聘者 2 分钟浏览路径

### 0:00–0:20：确认是什么

看到 Hero、目标受众、四个模块和 synthetic boundary。此时应知道这不是实时企业系统，而是一个公开 People Analytics 产品案例。

### 0:20–0:50：确认我做了什么

阅读贡献模块和 AI-assisted build：UI 迁移、数据层重建、指标契约、验证与安全边界。AI 参与方式用一句话说明，不展开成工具清单。

### 0:50–1:30：打开一个核心页面

推荐默认引导到“预算进度”或“薪资分析”，从筛选、图表 Tooltip、展开明细中看到真实交互，而不是停留在静态宣传语。

### 1:30–1:50：查看结构决策

点击系统架构，看到 Internal vs Public 双层图和 `synthetic JSON → adapter → calculation → UI`。

### 1:50–2:00：确认边界和下一步

看到明确的“不迁移权限/数据库/企业 KPI”说明，以及 README / audit / contract 的链接。招聘者应知道哪些能力已完成、哪些是有意排除，而不是误以为遗漏。

## 10. 明确禁止展示的内容

Overview 和 Architecture 均不得出现：

- 原企业名称、域名、URL、数据库名、表名、文件名或本机路径；
- 真实姓名、邮箱、手机号、员工号、Open ID、session、token 或 secrets；
- 原组织树、岗位名、城市名单、真实薪资区间或原始截图；
- 企业 KPI、订单、营收、费用率、奖金/提成规则或异常排名；
- 原始 CSV、工作簿、导出文件、source row、source file 或内部 Git 历史；
- 可提交的上传、映射激活、权限变更、数据库写入或“实时健康检查”按钮；
- 没有真实后端支撑的登录、管理员、数据库管理或多租户承诺；
- 把 synthetic coefficient、employer_cost 或 role multiplier 描述成法定费率、公司费率、市场标准或真实岗位价值。

## 11. 后续实现 Phase 划分

### Phase 0：文案与证据收口

- 确认 Hero、职责、边界和四张入口卡文案；
- 整理公开截图位置和已通过的验证清单；
- 不改业务页面和数据。

### Phase 1：Portfolio Overview

- 用上述 IA 替换当前 Coming later 占位页；
- 只增加入口、说明、职责、AI workflow、数据边界和静态链接；
- 不接原总览 API，不新增 KPI 计算，不修改四个冻结页面。

### Phase 2：System Architecture

- 用 Internal/Public 双层架构图替换当前占位页；
- 加入 Data Import / Mapping case study 卡片；
- 链接审计报告、公开 contract 和验证命令；
- 不实现数据库管理、权限管理或导入后台。

### Phase 3：可选治理展示

- 仅在招聘目标明确偏 HR Tech / Analytics Engineering 时考虑静态 Data Governance section；
- 展示 public schema、唯一键、质量规则和 adapter 边界；
- 仍不连接数据库、不接受持久化上传、不模拟登录。

### 每个实现 Phase 的验收门

- Budget / Salary / Evaluation / Detail 无视觉或数据回归；
- static export 和 GitHub Pages basePath 正常；
- 无 `/api/`、数据库、auth/session/permission 运行时依赖；
- console 无 runtime error；
- 文案不暗示真实企业数据或后台能力。

## 12. 最终决策

1. **Portfolio Overview**：值得实现，但必须是招聘作品集信息架构，不是原总览迁移。
2. **System Architecture**：值得实现，重点展示 Internal/Public 边界、adapter 数据链和工程取舍。
3. **数据导入 / 映射配置**：只作为 case study 内容，不恢复可操作后台。
4. **数据库管理**：暂不做独立页面；如需要，放入静态 Architecture / Governance section。
5. **权限管理**：不迁移；只说明生产系统安全边界。
6. **下一步最优顺序**：先实现 Portfolio Overview，再实现 Architecture；保持四个分析页面冻结。

本设计的成功标准不是“公开仓库包含原系统所有菜单”，而是招聘者能在两分钟内理解：这个产品解决什么问题、候选人做了哪些工程和产品判断、数据为什么可信，以及哪些能力被有意安全地排除。
