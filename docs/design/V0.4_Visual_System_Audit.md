# V0.4 Visual System Audit

状态：只读审计与设计方案（不改变 v0.3 冻结基线）  
范围：Overview、Budget、Salary Analysis、Labor Cost Evaluation、Detail Query  
审计对象：当前公开 GitHub Pages portfolio 与仓库内页面/CSS实现

## 1. 结论摘要

v0.3 已形成稳定的公开产品视觉语言：浅灰页面背景、白色内容表面、蓝色主色、细边框、低阴影、中文业务标题与 Ant Design 控件。五个页面在外壳、导航、数据边界和基础可读性上是统一的。

但页面 CSS 仍是按迁移批次分别提取的：Budget 使用一套 budget token，Evaluation 和 Detail 使用局部硬编码，Salary 保留较多原页面 utility 类映射，Overview 使用独立的 portfolio 视觉层。因此“看起来属于同一个产品”成立，但还没有形成可复用、可治理的 Design System。

V0.4 建议先做 token 与基础组件治理，再做页面级微调。不得借统一化之名改变指标、数据、模块顺序或已验收交互。

## 3. 当前统一性审计

### 3.1 页面宽度与留白

- 共同外壳使用 `.app-content { padding: 24px; background: #f5f7fa; }`，桌面端内容起点一致。
- Budget 通过负 margin 抵消外壳 padding，再使用自己的 24px 内边距；Evaluation 同样使用 `margin: -24px; padding: 24px`。
- Overview 使用 `max-width: 1280px` 居中，业务页多依赖父级宽度；Evaluation 内容最大宽度为 1440px；Salary/Detail 没有同等明确的内容 max-width。
- 移动端分别使用 14px、21/4px、局部页面 padding，视觉密度不同。

判断：外壳一致，但页面容器契约不一致，是跨页面最明显的治理机会。建议统一“外壳 padding + 内容 max-width + mobile gutter”，保留明细宽表的内部滚动，不统一成同一表格宽度。

### 3.2 Header / Filter 布局

- Budget：sticky filter bar，标题与控件同一白色容器，允许换行。
- Salary：标题/说明与筛选器纵向排列，控件间距较宽。
- Evaluation：白色 header card 内左右分布，窄屏切为纵向。
- Detail：标题与导出按钮一行，筛选器为密集 grid，移动端单列；数据类型 segmented control 在移动端已采用控件自身局部滚动。
- Overview：无业务筛选器，以 Hero CTA 和模块入口为主。

判断：业务语义导致的布局差异应保留；可统一的是标题层级、filter label、control height、control border/radius、窄屏断点和 focus 状态。

### 3.3 KPI 卡片与信息表面

- Budget 指标卡偏仪表盘：进度环、金额、预算对比、状态标签，卡片较高。
- Evaluation 使用 4 张紧凑 KPI 卡，数字大、说明短，服务联动分析。
- Salary 以岗位结构卡和分析卡为主，不应强行改成 KPI 卡墙。
- Detail 没有 KPI 卡，摘要行与宽表承担信息密度。
- Overview 使用 Hero、轻量信息块、模块卡，不应变成业务 KPI dashboard。

判断：卡片“角色”不同，不能统一高度或内容模板；应统一 surface token、标题/数值 typography、边框和交互状态。

### 3.4 Radius / border / shadow

当前常见值包括：

- 4px：状态 tag、小标签
- 6–8px：控件、局部明细、按钮、岗位卡
- 10–14px：业务卡片
- 16–18px：Overview Hero/header
- 边框主要为 `#e3e8ef`、`#e5e7eb`、`#e2e8f0`、`#dfe6ed` 等相近但重复的值
- 阴影从无阴影、`0 3px 10px` 到 Overview Hero 的大面积阴影不等

判断：页面并不凌乱，但重复灰色和 radius 值会增加维护成本。建议统一为 3 个表面层级与 4 个 radius 层级；Hero 的大阴影作为品牌层例外保留。

### 3.5 字号层级

- 全局正文基础约 13–14px，辅助说明约 11–12px。
- Overview 标题明显更大（Hero 42–68px，区块标题约 25–29px）。
- Budget 页面标题 20px，Evaluation 业务标题约 22px，Detail h1 22px，Salary h1 24px。
- Salary 仍保留大量 utility 映射（`text-xs`、`text-sm`、`text-3xl`），与其他页面的语义 class 不完全一致。

判断：Overview 的展示级标题应保留；四个业务页应收敛到统一的 page title / section title / body / meta 层级，避免同一层级出现 20、22、24px 的漂移。

### 3.6 图表配色与状态色

当前主色以 `#4f6faf` / `#4d9589` 为主，Salary 另有蓝、青、香槟黄、玫瑰色以及多组渐变，Evaluation 使用蓝/青，Budget 使用 budget token 的蓝、绿、黄、红状态色。

建议：

- 分析系列色：主蓝、青绿、辅助紫/琥珀；同一语义在不同页面使用同一色。
- 状态色：healthy/success、near/warning、over/danger、missing/neutral；状态色只表达数据状态，不表达未经定义的业务价值判断。
- Salary 城市层级与薪资组成属于页面语义色，应保留专用映射，但颜色来源改由 token 引用。
- Tooltip 背景、轴文字、网格线和空状态颜色应统一。

### 3.7 表格样式

- Budget 表格偏卡片内摘要与展开明细。
- Salary 的岗位/等级比较以图表和说明为主。
- Evaluation 明细表强调精确指标，局部滚动。
- Detail 是操作型宽表：固定左列、表头、排序、分页、聚合和局部横向滚动。

必须保留的个性：Detail 的列密度、固定左列和宽表滚动；Budget 的展开层级；Evaluation 的精确数值表。可统一的部分是表头背景、行高、边框、数字对齐、空状态和 focus/hover。

### 3.8 Desktop / Mobile 响应式

- Overview：桌面 Hero/模块网格，移动端单列堆叠。
- Budget：5 列 → 3 列 → 2 列 → 1 列，SideNav 在移动端隐藏。
- Evaluation：4 KPI → 2 → 1，趋势双列 → 单列。
- Salary：通过 utility breakpoint 重排，图表和结构区保留局部滚动。
- Detail：筛选 grid → 单列，宽表保持局部横滚；segmented control 已修复为控件内部滚动，不再造成页面级溢出。

判断：响应式策略总体正确，但断点命名、页面 gutter 和“什么可以局部滚动”的约定应文档化。不得用全局 `overflow-x: hidden` 取代布局约束。

### 4.2 推荐 typography roles

| Role | 建议 | 适用 |
|---|---:|---|
| Page title | 22px / 30px / 700 | 业务页标题 |
| Section title | 15–18px / 24px / 650–700 | 卡片与模块标题 |
| KPI value | 25–28px / 1.15 / 700–800 | Budget/Evaluation 数值 |
| Body | 13–14px / 1.7 | 解释与正文 |
| Meta | 11–12px / 1.5 | 标签、来源、口径说明 |
| Portfolio hero | 独立展示级 scale | 仅 Overview |

### 4.3 推荐基础组件契约

- `PageFrame`：负责页面背景、gutter、max-width、移动端边界。
- `PageHeader`：标题、副标题、右侧 action；不承载业务计算。
- `FilterBar`：统一 label、control height、gap、wrap/fallback；页面可决定横向或纵向布局。
- `SurfaceCard`：统一 border/radius/background，默认不带重阴影。
- `MetricCard`：只统一外观与 typography，不统一指标数量或业务内容。
- `ChartCard`：统一标题、legend、tooltip、空状态和容器约束。
- `DataTable`：统一表头、行高、数字对齐、empty/loading/error；允许页面指定 fixed columns 与 local scroll。

## 5. 必须保留的页面个性

| 页面 | 不应被统一抹平的特征 | 原因 |
|---|---|---|
| Overview | Hero、叙事 sections、四模块入口、Architecture CTA | 这是招聘者入口，不是业务 dashboard |
| Budget | 预算/实际/使用率状态、5 卡布局、展开明细 | 业务问题是预算控制，不是单纯趋势 |
| Salary | 岗位结构卡、薪资组成、城市层级和横向比较 | 需要同时容纳结构、组成和多维比较 |
| Evaluation | 4 KPI、成本与 HC 双轴趋势、grouped bar + structure gap | 页面信息架构已通过验收 |
| Detail | 宽表、固定左列、排序/分页/聚合/CSV | 操作型查询体验是页面价值 |

## 6. 当前明显影响专业感的问题

按优先级排序，不表示本轮已修改：

### P0：视觉治理风险

1. **容器契约分散**：Budget/Evaluation 的负 margin 方案、Overview 1280 max-width、Evaluation 1440 max-width、Salary/Detail 的独立宽度规则并存，新增页面容易重新产生边界差异。
2. **Design token 重复且未共享**：相近的灰色、边框和 radius 在三套页面 CSS 中重复出现，状态色也有页面局部命名。

### P1：跨页一致性问题

3. **业务页标题层级漂移**：Salary 24px、Evaluation/Detail 22px、Budget 20px；不是功能问题，但降低产品整体的秩序感。
4. **Card surface 不同**：Budget/Evaluation/Detail 多为无阴影细边框，Salary 局部使用 12/16px radius 与阴影，Overview 又有明显 Hero 阴影。
5. **筛选区密度不同**：Budget sticky、Evaluation header card、Salary vertical filter、Detail dense grid；应统一控件规格和响应式原则，而不是统一布局方向。

### P2：可读性与维护性问题

6. **Salary utility CSS 映射较多**：迁移后仍有大量 class-to-style 规则，设计 token 不易追踪。
7. **图表颜色以局部字面量为主**：跨图表保持语义色需要人工记忆，Tooltip/axis/grid 也未完全共享。
8. **状态色语义需集中说明**：Budget 的预算状态与 Salary 的薪资分类色不能混用；应由 token 文档定义允许范围。
9. **移动端滚动边界需要契约化**：Detail 表格和 Salary 结构区允许局部横滚，页面根节点不允许；这一边界应在基础组件规范中明确。

## 7. 页面级优化优先级

| 优先级 | 页面 | 建议 | 不改变的内容 |
|---|---|---|---|
| 1 | Detail | 抽出 FilterBar/DataTable tokens，统一表头、控件和滚动边界 | 宽表字段、固定列、排序、分页、聚合、CSV |
| 2 | Evaluation | 接入 PageFrame、SurfaceCard、ChartCard 和统一 typography | 4 KPI、趋势比例、grouped bar、指标公式 |
| 3 | Budget | 将现有 budget tokens 对齐到 shared tokens，保留预算状态专用色 | 预算口径、5 卡布局、展开交互 |
| 4 | Salary | 逐步将 utility 映射替换为语义 tokens，保留图表个性 token | 薪资计算、结构卡、城市层级、图表交互 |
| 5 | Overview | 仅对 spacing/color primitives 做接入，不把叙事页卡片化 | Hero、信息顺序、CTA、招聘叙事 |

## 8. 后续实施 Phase

### Phase 0：Token contract

只新增/整理设计 token 与文档，建立颜色、surface、radius、spacing、typography、breakpoint 和滚动边界契约。不得改页面视觉结果。

### Phase 1：基础外壳与控件

在不改业务数据的前提下，统一 PageFrame、PageHeader、FilterBar、SurfaceCard 的基础规格；先 Detail 与 Evaluation 做回归，再处理 Budget。

### Phase 2：图表与表格规范

统一 ECharts tooltip、轴、legend、空状态和表格表头/行高/数字对齐。页面专用语义色通过 token 显式声明，避免把状态色和分类色混为一谈。

### Phase 3：Salary / Overview polish

清理 Salary utility 样式映射，接入 shared primitives；Overview 只做 spacing 和 primitive 对齐，保持独立的 portfolio hierarchy。

### Phase 4：跨 viewport QA

固定 1440、1280、768、390 四档验收矩阵：页面级 `scrollWidth <= clientWidth`，允许明确标记的表格/结构区局部滚动；逐页检查 Console、资源、导航和交互回归。

## 9. 建议的验收标准

- 不改变任何指标、synthetic data、adapter、计算逻辑、模块顺序和交互语义。
- 业务页 desktop content frame 与 mobile gutter 有统一契约。
- 页面根节点无横向溢出；局部滚动容器有明确边界。
- Card、filter、table 的 border/radius/typography 使用 shared token 或有文档化例外。
- Overview 仍然是 portfolio narrative；Detail 仍然是高密度操作表；Budget/Salary/Evaluation 仍保留各自分析语义。
- 每个 Phase 都运行 `npm run test:data`、`npm run build`、`GITHUB_ACTIONS=true npm run build`、`git diff --check`，并进行四档浏览器回归。

## 10. 审计结论

v0.3 不需要重新设计。最值得做的是把已经验证过的视觉决策提炼成可复用的 token 与基础组件契约，再以页面个性为边界逐步接入。推荐从 Detail/Evaluation 的跨页基础规格开始，最后处理 Salary utility 清理与 Overview 的轻量 primitive 对齐。
