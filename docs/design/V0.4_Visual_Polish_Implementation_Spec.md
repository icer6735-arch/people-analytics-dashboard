# V0.4 Visual Polish Implementation Contract

状态：实施前冻结契约  
阶段：V0.4 Portfolio Product Polish  
前置基线：`v0.3-public-baseline`

本契约把已确认的 V0.4 实施边界写成可验收、可回退的规则。它不是页面重设计方案，也不授权本阶段修改任何业务代码、数据或计算逻辑。

## 1. V0.4 总目标

V0.4 是 Public Portfolio 的视觉治理阶段，不是页面重设计。

目标是让 Overview、Budget、Salary Analysis、Labor Cost Evaluation、Detail Query 看起来属于同一成熟产品，形成共享视觉语言，同时保留 V0.3 已冻结的业务信息架构、页面结构和核心交互。

## 2. 必须冻结的原则

1. 不重做任何业务页面的信息架构。
2. 不调整四个业务模块的顺序。
3. 不删除或新增业务功能。
4. 不修改 synthetic data、adapter、计算逻辑或业务结果。
5. 不修改筛选作用域和业务交互语义。
6. 不为了视觉统一强制所有页面使用同一布局。
7. 不把业务页改造成统一的通用 SaaS Dashboard。
8. Overview Hero 和叙事结构继续保持独立作品集表达。
9. 不恢复原系统后台、API、数据库、权限或身份能力。

## 3. 页面宽度与滚动边界

“统一页面宽度”不得实现为所有页面共享同一个 `max-width`。

统一的是：

- App shell；
- 页面左右 gutter；
- breakpoint 规则；
- 页面 padding 逻辑；
- 页面级与局部滚动边界。

页面内容宽度按页面类型区分：

- **Overview**：narrative / portfolio width；
- **Budget / Evaluation**：dashboard wide；
- **Salary / Detail**：data visualization / wide-table width。

Salary 和 Detail 必须继续允许页面内部的局部横向滚动。禁止用全局 `overflow-x: hidden` 掩盖布局问题；页面根节点必须通过正确的 `min-width: 0`、容器约束和局部滚动容器解决溢出。

## 4. 允许统一的内容

V0.4 只允许治理以下基础视觉规格：

- shared color tokens；
- typography hierarchy；
- spacing scale；
- border；
- radius；
- shadow policy；
- surface / background；
- control height；
- Filter Bar 基础视觉语言；
- Card 基础视觉语言；
- KPI typography；
- Chart container 基础规格；
- Table header / border / row density 基础规格；
- responsive breakpoints；
- focus / hover / disabled 等基础状态。

这些统一只影响表达层，不得改变指标、数据、组件顺序或交互语义。

## 5. 禁止统一的业务结构

以下结构属于页面业务个性，继续冻结，不得为了视觉统一而替换。

### Budget

- 五张预算指标卡；
- 预算 / 实际 / 使用率状态；
- sticky filter bar；
- 当月 / 累计；
- 三类预算比较区；
- 明细展开结构；
- KPI 场景 → 分组 → 科目 → 明细。

### Salary Analysis

- 岗位薪资结构卡；
- 横向结构区；
- 薪资趋势；
- 城市 / 岗位层级比较；
- 页面内部需要的局部横向滚动。

### Labor Cost Evaluation

- 现有 KPI 数量；
- 当前趋势关系；
- 岗位结构；
- grouped bar / structure gap 等当前业务布局。

### Detail Query

- 高密度宽表；
- 固定列；
- 搜索、筛选、聚合、分页、CSV；
- 表格局部横向滚动。

### Overview

- Hero；
- 叙事 sections；
- 四模块入口；
- Architecture CTA；
- 不改造成 KPI dashboard。

## 6. 视觉治理优先级定义

原 Visual System Audit 中的 P0/P1/P2 是视觉治理优先级，不是生产故障等级，不自动意味着必须立即修复线上问题。

优先处理跨页基础契约；只有在确认不影响业务结构和交互后，才处理页面局部 polish。

## 7. 冻结的实施顺序

严禁一次性修改五个页面。每个 Phase 必须独立验收、独立 commit、独立回退。

### Phase 0A：Design Token Contract

只定义 shared color、typography、spacing、border、radius、shadow、surface、status 和 control tokens，不修改页面视觉结果。

验收重点：token 命名、语义、例外范围和页面映射关系明确。

### Phase 0B：Shell Contract

定义 gutter、page width category、breakpoint、padding 逻辑和 scroll boundary，仍不修改业务页面。

验收重点：每类页面的容器责任和局部滚动边界明确。

### Phase 1：单页低风险试点

优先选择 Evaluation 或 Detail 其中一个，只实施基础视觉规格。试点完成后必须人工确认，未经确认不得进入下一阶段。

### Phase 2：另一个业务页

将已经验收的基础规格应用到另一个试点页，保留该页全部业务布局与交互。

### Phase 3：Budget

对齐 shared tokens 和基础 surface，但保留预算状态、sticky filter、5 卡和展开结构。

### Phase 4：Salary

逐步治理 utility CSS 映射，保留薪资结构、趋势、城市/岗位比较和局部横滚。

### Phase 5：Overview primitive alignment

只对齐基础颜色、spacing、typography primitive；不改变 Hero、叙事顺序、模块入口和 Architecture CTA。

### Phase 6：Cross-page / cross-viewport QA

完成五个页面的跨页面和跨 viewport 回归，不新增视觉设计。

## 8. 每个 Phase 的验收门

每个 Phase 必须验证 `1440`、`1280`、`768`、`390` 四档 viewport，并确认：

- 页面级无 horizontal overflow；
- 原有局部横向滚动仍正常；
- 筛选器和交互无回归；
- 图表没有截断；
- 表格固定列正常；
- 页面信息层级没有变化；
- synthetic data 和业务结果完全不变；
- Console 无 runtime error；
- `npm run test:data` 通过；
- `npm run build` 通过；
- `GITHUB_ACTIONS=true npm run build` 通过；
- `git diff --check` 通过。

视觉变更必须能够只回退当前 Phase，不得依赖跨 Phase 的隐式修改。

## 9. 明确不在 V0.4 范围内

- 页面重设计或模块重排；
- 指标、数据、adapter、calculation、status policy 变更；
- synthetic 数据重新生成；
- 新增业务功能或删除现有功能；
- 恢复原企业 API、数据库、auth、session、permission；
- Architecture 页面实现；
- README、部署 workflow 或 GitHub Pages 配置变更；
- 任何未通过人工验收的批量视觉迁移。

## 10. 实施授权门

本契约只授权后续按 Phase 逐步实施，不授权当前立即修改代码。开始 Phase 1 前，应先确认：

1. 当前 `v0.3-public-baseline` 不被改写；
2. 工作区基线和目标试点页明确；
3. 本 Phase 的文件白名单明确；
4. 验收与回退方式明确；
5. 人工确认后才进入下一 Phase。
